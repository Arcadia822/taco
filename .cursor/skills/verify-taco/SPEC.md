## Intent and scope

Give a cold agent an executable path to prove the built Taco Complete browser app through real user actions. Class: workflow-process. Shape: script-backed-workflow, with a five-file feature map. The helper removes repeated lifecycle and evidence boilerplate; scenario modules keep consumer behavior explicit. CLI, optional extension, Lite and Tacobin need separate targeted runs; local Complete proof does not establish those surfaces.

## Runtime and evidence contract

Build production HTML, launch an immutable snapshot on an owned ephemeral loopback port, create a fresh Chromium context, run a read-only doctor, drive mapped entry points, retain before/after screenshots and ARIA snapshots, action log, browser trace, network log and result manifest. Mutation scenarios must observe the public read-only API and saved/downloaded state where applicable. Close owned resources in finally, including failed scenarios; retain all proof in `artifacts/verify-taco/`.

## Trigger checks

Should trigger: “verify Taco's saved HTML”; “prove Markdown editing in the actual Taco app”; “capture a Taco comment regression with screenshots”. Should not trigger: “install Taco”; “publish to Tacobin”; “review a diff without running the app”; “verify only the CLI”. The runtime description names Taco's built browser surface explicitly.

## Maintenance and validation

Read `SOURCES.md` for decisions and source provenance. Refresh mapped selectors whenever the UI entry changes, and add a recipe for each new entry point in an existing mapped feature. Keep exactly four H2 sections in each feature file, in the requested order. Keep leading YAML titles rather than duplicate H1 headings. Read `features/README.md` before choosing coverage. A single entry-point proof cannot stand in for all entries.

Validate leading skill frontmatter with skill-writer's quick_validate.py. Execute the helper's default browsing scenario after lifecycle changes. Exercise failure cleanup with a throwaway throwing scenario after cleanup changes. Retain evidence and check the named files after teardown. Do not add permanent tests that only inspect documentation text or helper wiring.

## Limits

Loopback Chromium verification is internal evidence and is not user-visible opening of the delivered file. Native file picker, directory permissions and OS browser transitions require their own interactive checks. Default production content has no Checkpoint graph; use a generated scratch Taco with a valid graph for that recipe. External systems remain unverified when their browser requests are blocked. Never use a credential-bearing live review as a fixture.
